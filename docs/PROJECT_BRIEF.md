# 项目简报

## 1. 项目名称

**AfterCare AI（售后智服台）**

## 2. 要解决的问题

中小电商商家的售后知识分散在政策文档、产品手册和客服经验中。顾客需要等待人工客服回答重复问题；客服还需要在多个系统之间查询订单、物流和退款状态。

AfterCare AI 将知识问答、业务查询和人工工单放入一个受控流程。AI 负责理解问题、检索知识、选择只读工具和生成解释；权限、确定性校验和高风险动作由传统代码与人工控制。

## 3. 目标用户

### 商家管理员

- 管理本租户的用户和角色。
- 上传、更新和删除知识文档。
- 查看文档处理状态、会话、反馈、工单和审计记录。

### 客服人员

- 查看分配给本租户的会话和工单。
- 接管 AI 无法处理的对话。
- 审批或拒绝需要人工确认的高风险操作。

### 顾客

- 咨询售后政策和商品使用问题。
- 查询自己的订单、物流和退款状态。
- 对回答进行评价或请求人工服务。

## 4. 第一版业务目标

1. 为有可靠知识依据的问题提供带引用的回答。
2. 使用受控工具完成订单、物流和退款状态查询。
3. 对低置信度、无答案和高风险请求安全地拒答或转人工。
4. 保证不同租户之间的文档、会话和业务数据相互隔离。
5. 建立可测试、可部署、可恢复的基础工程链路。

## 5. 核心业务链路

### 链路 A：知识问答

管理员上传文档 → 后台解析与索引 → 顾客提问 → 权限过滤与混合检索 → 重排 → 生成带引用的回答 → 顾客反馈。

### 链路 B：业务查询

顾客提问 → 系统识别查询意图 → 校验身份与参数 → 调用订单/物流/退款只读工具 → 生成可追溯的说明 → 写入审计日志。

### 链路 C：转人工

无可靠答案、工具失败或顾客要求人工 → 系统总结上下文 → 幂等创建工单 → 客服接管 → 保留完整处理记录。

## 6. 第一版范围

- 用户登录、JWT、角色权限和多租户隔离。
- 会话、消息、SSE 流式回复、停止生成和重新生成。
- PDF、Word、Markdown 文档上传、异步解析、版本和状态管理。
- Dense + Sparse 混合检索、重排、权限过滤、引用和拒答。
- 查询订单、物流、退款状态，创建工单和转人工。
- Tool 参数校验、权限、超时、重试、幂等和审计。
- LangGraph 单 Agent 工作流与 Checkpointer。
- 自动测试、Docker Compose、CI/CD、健康检查和回滚说明。

## 7. 明确不做

- 不实现多 Agent 协作。
- 不拆分微服务，不引入 Kubernetes。
- 不训练或微调基础模型。
- 不接入真实支付、真实退款或真实电商平台。
- 不处理真实客户隐私数据。
- 不开发语音客服、图片识别或复杂工作流编辑器。
- 不以替代全部人工客服作为第一版目标。

## 8. 受控 Beta 的成功标准

- 三条核心业务链路均可通过浏览器完整演示。
- 关键正向和失败场景存在自动化测试。
- 不同租户间的数据隔离有负向测试证明。
- 回答可以追溯到知识来源；没有可靠依据时不编造答案。
- 工具失败、模型不可用和服务重启时存在明确行为。
- 可以在一台 Linux 服务器上通过 Docker Compose 部署并使用 HTTPS 访问。
- 从代码提交到测试、镜像构建、迁移和部署形成可重复流程。

## 9. 学习成功标准

项目完成时，开发者能够独立解释：

- 每条核心业务链路的数据流和权限边界。
- 为什么使用工作流、Agent、Checkpointer 和后台任务。
- 文档更新与删除如何保持数据库和索引一致。
- Tool 超时、重试和重复调用如何处理。
- 模型不可用、迁移失败和部署失败时如何降级或回滚。
- 如何通过需求、验收条件、测试和小批次改动控制 AI 编码过程。
