## 使用方法

1. 本次要解决的业务问题是什么？
2. 请求或数据经过了哪些组件？
3. 最重要的设计选择是什么，为什么？

5. 至少一个失败路径通过什么测试证明？

## M1：可运行骨架

**业务目标**：建立从浏览器到 Vue、FastAPI、PostgreSQL、Redis 和 Qdrant 的最小可运行链路，并区分进程存活与系统就绪。

**批准范围**：提交 M0 本地基线；创建 M1 功能分支；生成前后端和 Compose 骨架；安装并锁定依赖；不提交 M1、不 push、不创建 PR。

**数据流**：浏览器状态页请求 FastAPI `/health/ready`；API 并行探测 PostgreSQL、Redis 和 Qdrant；前端根据 HTTP 状态和结构化结果展示整体与组件状态。

**关键决定与理由**：

- `/health/live` 不访问外部依赖，避免依赖故障导致编排系统反复重启仍然正常的 API 进程。
- `/health/ready` 检查必要依赖，未就绪时返回 503，避免故障实例继续接收业务流量。
- 数据服务仅暴露在 Compose 内部网络，避免宿主机端口冲突并减少无必要的攻击面。
- TypeScript 固定为 5.9.3，因为自动选择的 7.0.2 与当前 `vue-tsc` 不兼容。

**验证证据**：

- 后端 Ruff 检查通过，Pytest 3 个测试通过。
- 前端类型检查和生产构建通过。
- Docker API、Web、PostgreSQL、Redis 均达到 healthy；Qdrant 正常运行。
- Web、live 和 ready 接口均返回 200，ready 报告三个依赖 healthy。

**失败路径**：停止 Qdrant 后，live 保持 200；ready 返回 503 并标记 Qdrant unhealthy；恢复 Qdrant 后 ready 回到 200。

**本轮发现并修复的问题**：

1. 包管理器选择了不兼容的 TypeScript 7.0.2，导致 `vue-tsc` 无法启动。通过读取错误栈定位为工具链兼容性问题，将 TypeScript 锁定为 5.9.3 后通过。
2. Web 页面可访问，但容器健康检查使用 `localhost` 时解析到 IPv6，而 Nginx 仅监听 IPv4。健康检查改为 `127.0.0.1` 后转为 healthy。
3. 宿主机 5432 已由其他项目占用。没有停止未知容器，而是移除数据库、Redis 和 Qdrant 的宿主机端口映射，仅保留内部网络连接。

**仍不理解或未验证的内容**：

- 尚未创建数据库业务模型或 Alembic 迁移。
- 尚未加入 CI；当前证据只来自本机。
- 尚未验证停止整个 Compose 环境后重新启动的数据持久化。
- 第三方测试客户端产生两个弃用警告，当前不影响行为，后续升级依赖时需要关注。

**下次怎样更好地描述任务**：明确区分宿主机端口与容器内部端口，并要求基础服务默认不暴露到宿主机。

**最终交付状态**：

- M1 已以提交 `b3f5aea`（`chore: add runnable application skeleton`）进入 `main` 并推送到远程仓库。
- 最初的功能分支方案后来根据个人学习项目的工作方式调整为直接在 `main` 串行提交；上面的“批准范围”保留为当时决策记录，不代表当前状态。

## M2-A：租户管理员注册、登录与当前用户接口

**业务目标**：新商家能够创建首个管理员账号、使用密码登录，并通过受保护接口读取由服务器确认的用户、租户和角色。

**我批准的范围**：在 API 中引入 SQLAlchemy、Alembic、Argon2 和 JWT；实现 tenant、user、tenant membership、注册、登录、当前用户接口和相关测试；不实现前端登录、刷新令牌、成员管理或对话功能。

**数据流**：注册请求在一个数据库事务中创建 tenant、user 和 merchant_admin membership；登录以 Argon2 校验密码后签发带过期时间的 JWT；`/me` 先验证 JWT 签名和过期时间，再从数据库重新检查 user、tenant 和 membership 的启用状态。

**关键决定与理由**：JWT 仅用于定位 user，不将 tenant 或 role 作为持续可信的授权来源。每个受保护请求都回查数据库，因此停用 user、membership 或 tenant 后，已签发但未过期的 token 也会失效。数据库结构只通过 Alembic 管理，API 容器启动时会执行 `alembic upgrade head`。

**验证证据**：`uv run ruff check .` 通过；`uv run pytest` 通过 10 个测试；Web 类型检查和生产构建通过。Docker Compose 在独立项目与数据卷中成功构建并启动，live/ready 均返回 200。真实 PostgreSQL 完成 `upgrade → downgrade → upgrade` 并回到 `20260922_01`；容器验证了注册 201、登录 200、`/me` 200、错误密码 401，以及停用 membership 后原 access token 的 `/me` 为 401。

**失败路径**：重复注册返回 409 且事务不保留部分数据；错误密码、畸形/过期 token、停用 user/membership/tenant 均返回 401。

**仍不理解或未验证的内容**：生产密钥轮换、刷新令牌和主动撤销列表不在 M2-A 范围内；CI 尚未自动运行本次验证。

**下次怎样更好地描述任务**：把本机 Docker 可用性作为实现前检查项；这能在写完迁移前尽早识别真实 PostgreSQL 验证环境是否具备。

## M2-B：前端登录与会话状态

**业务目标**：让已注册商家管理员能够在浏览器中登录、刷新后恢复当前身份，并在令牌无效或主动退出后无法继续进入受保护页面。

**我批准的范围**：增加前端路由、登录页、`sessionStorage` 令牌状态、`/auth/me` 身份恢复、退出、自动化测试和状态文档；不实现刷新令牌、服务端撤销列表、成员管理或对话功能。

**数据流**：登录页提交邮箱与密码到 `/api/v1/auth/login`；浏览器仅在当前会话的 `sessionStorage` 中保存 Bearer token，随后调用 `/api/v1/auth/me` 获取服务器确认的用户、租户和角色。每次应用首次路由跳转都校验当前身份；校验失败则清除 token 并重定向到 `/login`。

**关键决定与理由**：使用 `sessionStorage` 而非长期持久化存储，减少共享设备或关闭浏览器后残留访问令牌的风险。前端不保存或信任 tenant、role 等授权事实；所有身份展示都来自后端 `/me`，业务权限仍由后端执行。

**验证证据**：前端 TypeScript 类型检查、Vitest 自动化测试和生产构建均通过。测试覆盖正常登录和 `/me` 请求携带 Bearer token、错误凭据不保存 token、失效或撤销 token 恢复失败后清理会话、以及退出清理会话。

**失败路径**：`/login` 或 `/me` 返回非成功状态、令牌响应格式异常、令牌过期或后端拒绝身份时，页面不会保留可用会话；受保护路由转到登录页。

**仍不理解或未验证的内容**：没有刷新令牌、服务端主动注销或撤销列表；关闭浏览器会话会要求重新登录。端到端 Compose 浏览器验证与 CI 自动化仍留待后续工作。

**下次怎样更好地描述任务**：前端认证任务应明确令牌生命周期、持久化范围，以及在 API 不可用时是否保留本地会话；本任务选择安全优先地清理本地状态。

## M2-D：SSE、停止与重新生成

**业务目标**：让已登录用户看到分段回复、能够停止正在生成的内容，并在保留原回复的前提下重新生成。

**批准范围**：SSE 事件、服务端停止与断连收尾、回复版本追踪、前后端交互、迁移、自动化测试和交接文档；不接入真实模型、RAG、Agent、反馈、提交或推送。

**数据流**：发送请求先通过认证和会话所有权检查，再提交用户消息与状态为 `generating` 的助手回复。响应依次发送 `started`、多个 `delta` 和终态事件。每个分段前读取持久化状态；停止、断连或协程取消都会停止后续分段并保存 `cancelled`。重新生成从已完成回复关联的用户输入建立新版本，完成后才切换当前版本。

**验证证据**：后端 Ruff 与 Pytest 通过，16 个测试覆盖 SSE 分段和持久化、停止、重新生成版本，以及既有会话隔离路径。前端 Vitest 通过 7 个测试，类型检查和生产构建通过；新增客户端测试覆盖 SSE 帧解析。

**仍未验证**：尚未在 Compose PostgreSQL 与真实浏览器中演练长连接断连、停止与迁移 `20260923_03` 的升级回退。当前确定性生成器只用于验证生命周期，不代表真实模型取消语义。

## M2-C：会话与消息持久化

**业务目标**：让已登录用户能够创建自己的会话、发送消息，并在页面刷新后从服务端重新读取保存的对话历史。

**我批准的范围**：新增会话与消息模型、Alembic 迁移、tenant-scoped API、确定性占位回复、最小前端会话界面、自动化测试和交接文档；不实现 SSE、RAG、Agent、停止、重新生成、反馈、提交或推送。

**数据流**：请求先经 Bearer token 与数据库回查得到可信 user、tenant 和 membership；创建会话时服务端写入该 tenant 与 owner。查询会话时同时按 conversation id、tenant id 和 owner user id 过滤。发送时在同一提交中保存 user 消息与 assistant 占位回复，随后前端从 API 读取完整历史。

**关键决定与理由**：tenant 和 owner 不由客户端传入，避免伪造身份边界。对跨租户和非所有者资源统一返回 `404`，避免泄露会话是否存在。确定性回复只用于先验证持久化链路，SSE 与真实生成将由 M2-D 在稳定契约上实现。认证回查会开启 SQLAlchemy 的隐式事务，因此写入服务复用该请求会话并一次提交，而不是开启第二个外层事务。

**验证证据**：后端 `uv run ruff check .` 通过，`uv run pytest` 通过 13 个测试；新增测试覆盖创建、发送、重新读取、同租户不同用户隔离、跨租户隔离和空消息拒绝。前端 `pnpm test` 通过 6 个测试，`pnpm typecheck` 与 `pnpm build` 通过。独立 Compose 项目的 PostgreSQL 17 从空库依次执行 `upgrade head → downgrade 20260922_01 → upgrade head`，最终回到 `20260923_02 (head)`；首次升级后的表、外键、角色约束和索引符合设计，回退后身份表保留而会话表移除。临时容器、网络和数据卷随后删除，原项目服务保持健康且数据库 revision 仍为 `20260922_01`。

**失败路径**：非所有者与跨租户读取会话均为 `404`，列表不会出现对方会话；空白消息为 `422` 且数据库不保存任何消息。

**仍不理解或未验证的内容**：Docker Desktop 安装在未加入当前 PATH 的用户目录；原长期运行环境仍处于 `20260922_01`，尚未重建并通过 Compose 做 M2-C 浏览器端到端验证。SSE 取消、消息版本、重新生成和反馈仍是后续 M2-D/M2-E 工作。

**下次怎样更好地描述任务**：对于依赖认证的写接口，应在设计时明确认证依赖的数据库事务边界，避免业务服务再次开始外层事务。
