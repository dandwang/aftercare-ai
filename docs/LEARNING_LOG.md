# 学习日志

这份日志不记录“今天看了多少课程”，而记录实际完成的能力、证据、问题和下一步。每个里程碑结束时至少更新一次。

## 使用方法

每次开发结束后，用自己的话回答：

1. 本次要解决的业务问题是什么？
2. 请求或数据经过了哪些组件？
3. 最重要的设计选择是什么，为什么？
4. 正常路径通过什么测试证明？
5. 至少一个失败路径通过什么测试证明？
6. 哪一部分仍然不理解或尚未验证？
7. 如果重新做一次，会怎样把任务描述得更清楚？

## Vibe Coding 任务模板

```text
业务目标：用户最终能够做什么？

当前范围：本次只实现什么？
非范围：本次明确不做什么？

验收条件：
1. Given / When / Then ...
2. Given / When / Then ...

约束：安全、兼容、性能或技术限制是什么？

执行要求：
先只读分析现有代码，给出方案、预计改动、验证计划和风险。
得到批准后再修改代码。完成后运行相关测试并解释关键设计。
```

## M0：项目定义

### 完成内容

- 选择“多租户电商售后 AI 客服与工单系统”作为主项目。
- 确定三类用户和三条核心业务链路。
- 将第一版范围与非范围明确分开。
- 建立需求编号、验收案例和初始架构决策。
- 确定使用小任务、先方案后实现、测试验证和 Git 检查点的协作方式。

### 当前理解检查

- [ ] 我能解释为什么第一版选择模块化单体，而不是微服务。
- [ ] 我能说出三条核心业务链路。
- [ ] 我能解释为什么模型不能直接决定租户身份和权限。
- [ ] 我能解释为什么查询订单和执行退款的风险不同。
- [ ] 我能说出“功能看起来能用”和“通过验收”的区别。
- [ ] 我能使用任务模板描述下一项功能。

### 尚未验证

- 本地 Docker 运行条件。
- 模型与 Embedding 服务选择、凭据和预算。
- Python、Node.js 和包管理工具版本。
- Linux 部署服务器、域名和证书条件。

### 下一步

进入 M1 前先进行只读环境检查，然后确定版本与目录结构。M1 的第一个实现任务只建立可启动、可健康检查的最小骨架，不加入登录、RAG 或 Agent 业务逻辑。
