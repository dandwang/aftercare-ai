1. 当前回复仍经过 `demo_reply` / `reply_text` 的确定性占位逻辑；SSE 分段不是模型流。尚无知识检索或真实模型适配器。

## 2 业务目标与范围

最终正常演示：商家管理员上传“签收后七天内可退货”的模拟政策，后台完成处理；同租户顾客询问退货期限，获得带文档名称、版本和片段定位的回答。没有海外退货费用依据时明确拒答。管理员上传十五天的新版本，成功后回答只使用新政策；删除文档后，新问题和重新生成均不再使用它。

本轮范围包括 Markdown、可提取文本的 PDF、Word `.docx`；本地 MinIO 原文件存储；Celery 异步解析和索引；文档版本与处理状态；Dense + Sparse 混合召回、融合与真实重排；后端租户和可见性过滤；真实模型带引用回答；明确拒答；管理界面、引用展示和正常全链路回归。

不默认加入扫描 PDF OCR、旧 `.doc`、复杂表格还原、网页抓取、语义切分平台、多个模型自动切换、自治 Agent、订单工具、真实退款或工单。工单与 Agent 路由留给 M4；“建议转人工”在 M3 只是一条提示。可靠队列投递、自动补偿、全量并发故障演练、大规模评测、CI 和部署属于后续阶段。上传限制、基本权限、租户隔离、脱敏及更新删除的正常正确性仍必须实现。

## 4 建议架构与稳定契约

### 模块与数据流

沿用 FastAPI 模块化单体。Knowledge 负责文档生命周期；Retrieval 负责索引、过滤和证据排序；Generation 负责模型适配与回答；Conversations 继续负责用户消息、回复版本和 SSE 生命周期。M3 不提前引入 LangGraph。

```text
管理员 → 认证及管理权限 → 保存 MinIO 原文件 → PostgreSQL 文档/版本/任务
→ 提交数据库事务 → 投递 Celery → Worker 解析/清洗/切分
→ PostgreSQL Chunk → Dense/Sparse → Qdrant 写入完成
→ PostgreSQL 原子切换 active_version_id

用户消息 → tenant + owner 检查 → 获取可访问的生效文档版本
→ 带过滤条件的 Dense/Sparse 召回 → 融合 → 数据库复核 → 重排
→ 证据门槛 → 完整提示词预算 → 冻结证据与上下文
→ 模型生成并校验引用 → SSE 输出 → 保存回复及引用
```

数据库、MinIO 和 Qdrant 没有一个共同事务。数据库中的生效版本是权威；不能把 Qdrant 的 payload 标记当成唯一有效性判断。

### 权限草案

可见性仅分 `customer_visible` 和 `staff_only`；都只在认证用户自己的租户内有效，不代表互联网公开。

| 操作 | merchant_admin | support_agent | customer |
|---|---|---|---|
| 上传、更新、删除文档，查看处理任务 | 本租户允许 | 403 | 403 |
| 在自己的会话检索 customer_visible | 允许 | 允许 | 允许 |
| 在自己的会话检索 staff_only | 允许 | 允许 | 不返回 |
| 查看引用来源片段 | 再检查租户、可见性和关联会话所有权 | 同左 | 同左，禁止内部文档 |
| 读取其他用户会话或上下文 | 404 | 404 | 404 |
| 使用跨租户文档/任务/Chunk UUID | 404 | 404 | 404 |

角色与可信 tenant 不接受请求或模型指定。上传时明确选择可见性，建议默认 `staff_only`；演示政策需管理员主动选择 `customer_visible`。任务中 tenant 从已持久化版本推导，不能只信任队列参数。自定义成员 ACL 和文档共享配置不在当前范围。

### 数据模型草案

| 表 | 最小字段或约束 | 权威职责 |
|---|---|---|
| `knowledge_documents` | id、tenant_id、title、visibility、active_version_id、deleted_at、created_by | 文档归属、权限与当前版本 |
| `document_versions` | id、tenant_id、document_id、version_number、object_key、file_type、checksum、status、error_code、error_summary、parser/chunker/index 配置标识 | 原文件及处理状态；document + version_number 唯一 |
| `document_jobs` | id、tenant_id、version_id、task_id、status、stage、started_at、finished_at | 可查询的异步任务状态，不仅依赖 Celery result backend |
| `document_chunks` | id、tenant_id、version_id、chunk_index、text、locator、token_count、point_id | 引用原文与位置；version + chunk_index 唯一 |
| `message_citations` | id、tenant_id、message_id、document_id、version_id、chunk_id、citation_label、title/locator/excerpt 快照 | 绑定具体回复版本的引用，不跟随当前版本移动 |
| 生成快照扩展 | 检索问题、实际证据 ID、索引/模型配置标识、提示词格式、预算；usage 若供应商返回 | 可解释该回复实际使用的证据和模型 |

实施时确定引用快照的字段与外键策略。删除文档不级联删除消息、反馈或历史引用；引用展示按当前权限判断是否可展开，并标记来源已删除或已替换。真实模型 usage 与本地预算估计分开保存，不能混为账单。

### 状态、版本与基本幂等

版本正常流转为 `queued → parsing → parsed → indexing → ready`；任一处理步骤失败进入 `failed`。任务单独记录当前 stage。`parsed` 只说明 Chunk 可读取，不能声明可检索；M3-D 完成索引之后才允许 ready。

更新创建 version 2，version 1 仍生效；新索引写入确认完成后，在数据库事务中验证新版本 ready、文档未删除，再切换 active 指针。失败时不切换。删除先在数据库标记 deleted 并清空 active 指针，让新检索立即排除，再清理该文档全部版本的 Qdrant points 与原文件；失败记录清理状态，后续手动重试。

使用 version + chunk_index 推导稳定 point UUID，重复 upsert 不追加副本。已 ready 的同版本任务重复执行可直接返回。默认单 Worker、串行文档更新，并用简单状态条件防止已删除文档被任务重新激活；不扩展成通用并发恢复框架。

### 检索过滤与预算

1. 从后端身份获取 tenant 和角色，查询数据库允许访问、未删除且 active 版本 ready 的集合。
2. Dense、Sparse 两条召回都带相同 tenant、允许版本及可见性过滤；候选进入重排和模型前再按数据库复核。少量演示文档可用 active version ID 白名单，规模化方案以后再评估。
3. 返回 Chunk ID 后从数据库取得权威原文与 locator，避免索引残留或 payload 内容成为业务事实。
4. 参考起点：两路各取 20 条、融合后重排最多 20 条、最终证据最多 4 条。它们是待问题集校准的初值，不是已验证最优参数。
5. 证据、引用标签、系统说明、摘要、历史、问题和供应商包装都纳入最终输入预算。超过预算先裁剪低优先级历史与证据，不裁断来源标识，不删除原消息；必要输入仍放不下则明确拒绝本次生成。
6. Dense、融合和 Rerank 的分数不是统一概率。依据小型正反问题集确定“证据足够”的模型相关规则，不直接写死通用 `0.7` 阈值。

旧会话中“七天”的历史回答不是当前政策依据。更新、删除后再次提问或重新生成都重新检索；新证据优先于历史，无新依据时不得用旧助手答案继续回答已经删除的政策。

## 5 分阶段开发步骤

以下文件均为预计变更位置。除已存在文件外，其余目录、接口和命令属于待实现草案。每个子任务开始时再核对当前代码和实际范围，未经批准不自动跨阶段写代码。

### M3-A 开发契约与环境选型

**业务目标**：把会影响后续所有步骤的权限、状态、存储、模型和费用条件先确定，让下一步不依赖临时猜测。

**执行顺序**：

1. 开发者核验 main、远程 SHA、工作区和 M2 契约；按用户分支要求，创建新开发分支前 fetch 最新 origin/main。不要以这份计划推断允许直接在 main 开发。
2. 确认上述权限表、数据模型、状态和引用读取规则；明确第一个切片先做 Markdown，不一次接入所有解析器。
3. 对象存储建议本地 MinIO；任务建议 Celery + Redis、Linux Compose Worker，共享 API 镜像与领域代码。固定依赖和镜像版本，不使用 latest。
4. 记录机器 CPU、内存、可用磁盘和模型下载条件。优先评估本地多语言 Dense、Sparse 与重排适配，避免检索阶段依赖多个付费服务；FastEmbed 是候选，具体模型必须在锁定版本中存在并通过中文样本验证。
5. Sparse 可从 BM25 类方案评估，但必须验证中文分词、query/document 编码一致性；不能把中文全文按英文空格拆分就视为可用。
6. 用户确定真实回答走哪一家云模型或已有本地模型。云方案先确认 endpoint、模型名、凭据注入、单次输出和允许费用；本地方案先确认实际模型与流式协议。不把示例值当有效账号，不自动产生付费调用。
7. 将用户确认的决策写入 DECISIONS，初始未批准建议保持 Proposed；随后给出 M3-B 拟改文件、验收和风险，再等待实施批准。

**交付物**：确认过的权限/接口/状态契约、依赖选型、环境配置表、模拟资料清单；如模型选择仍待定，明确 M3-D 或 M3-E 的进入条件。

**预计文件**：本计划、`docs/DECISIONS.md`、`docs/STATUS.md`。需要可运行适配器探针时先单独确认代码范围。

**验证与完成条件**：能说明一个管理员上传的文档由谁读取、何时可检索、怎样失效；明确 Dense 维度、Sparse 编码、Reranker、Tokenizer 和模型标识，或明确何时补齐。B/C 只要求其存储、格式、状态契约已确定；D/E 要求相关模型条件已满足。

**学习重点与风险**：Embedding 找语义相近内容，Sparse 找词项相关内容，Reranker 重新判断问句与片段关系，LLM 组织回答。四者不能以一个“模型名”代替。中文效果、下载体积、授权用途和硬件成本可能影响选型。

### M3-B 文档后端与异步任务入口

**业务目标**：管理员可上传一份 Markdown 模拟政策，立即获得文档、版本和任务 ID，并能查询后台状态。

**执行顺序**：

1. 新增 knowledge 文档、版本、任务与 Chunk 模型及 Alembic 迁移；给 tenant、version 与任务查询加必要索引，建立可信关联。
2. 建立 MinIO 私有 bucket 和对象存储适配器；对象键由服务端 UUID 生成。API 与 Worker 使用相同 bucket/config；不允许浏览器匿名访问整个 bucket。
3. 新增管理员上传、列表、详情、版本和任务查询 API。初始仅支持 `.md`；明确文件大小初值，例如 10 MiB，并按流式累计字节验证，不只相信 Content-Length 或后缀。
4. 保存原文件，提交版本和任务记录，再投递 Celery。队列消息只放任务/版本 ID；投递失败记录可理解状态，不让正常任务永久显示成功。
5. Worker 读取已提交记录并重新验证文档归属和状态。使用独立进程的数据库生命周期；不要跨线程/事件循环复用 FastAPI 的 AsyncSession 或共享异步连接池。
6. 加入独立 M3 验证 Compose，包含 Worker、MinIO 与初始化；Worker 在迁移完成后消费。同步扩展管理审计动作和 document/job 资源 UUID 识别。

**预计文件**：`src/aftercare_api/knowledge/{models,schemas,router,service,storage,tasks}.py`、任务入口模块、`config.py`、`main.py`、`audit/middleware.py`、`alembic/env.py`、新迁移、`pyproject.toml`、`uv.lock`、`Dockerfile`、`.env.example`、`compose.m3.verify.yaml`、对应后端测试与 README。

**验证与完成条件**：独立 PostgreSQL 从 M2 head 升级且能回退重升级；管理员上传得到 202 和持久化 ID，MinIO 存在对象，Worker 能读取任务，接口能查询状态。顾客和客服直接管理请求为 403，跨租户 UUID 为 404。此阶段不把 queued/parsed 标成 ready。

**学习重点与风险**：异步任务是请求结束后由其他进程继续执行。数据库提交后再投递仍有故障窗口，当前仅做明确状态和人工重试入口，不引入事务 Outbox 或宣称可靠投递。

### M3-C 三格式解析与可追溯 Chunk

**业务目标**：同一份政策以 Markdown、文本 PDF、DOCX 上传，都能产生可定位的原文片段。

**执行顺序**：

1. 先完成 Markdown 解析，把上传 → Worker → parsed 跑通；再添加 PDF、DOCX，避免同时排查三个格式。
2. 统一解析输出为文本段和 locator：Markdown 标题/行范围、PDF 页码/页内片段编号、DOCX 段落/表格行编号。DOCX 不承诺固定页码。
3. 建议以 pypdf 处理可提取文本的 PDF、python-docx 处理 DOCX；清洗空行和噪声时保留否定词、数字、日期及来源位置，不替用户概括或改变政策。
4. 按段落/标题并受 Token 上限约束切分。可从 400 Token、60 Token 重叠评估；跨页 Chunk 保存完整 locator 范围。索引切分所用编码与生成预算编码分别记录。
5. 保存 Chunk 原文、序号、位置、Token、内容校验和及 parser/chunker 配置标识。重跑同版本任务不产生重复 Chunk；日志只记录 ID、数量和错误类型。
6. 解析无文本或不支持格式时写 failed 与脱敏原因；扫描 PDF 明确提示当前不支持 OCR。后续 D 消费 parsed，不提前激活。

**预计文件**：`knowledge/parsers/`、`knowledge/chunking.py`、`knowledge/tasks.py`、`knowledge/service.py`、依赖锁文件、`tests/fixtures/knowledge/` 与解析正常流程测试。

**验证与完成条件**：三份小型合成文件均含“签收后七天内可退货”，解析后句子和数字保持原义，所有 Chunk 有定位且满足大小限制。任务到 parsed，Chunk 可从数据库读出。选择一个无文本样本确认不会显示成功即可，不扩展格式故障矩阵。

**学习重点与风险**：解析、切分和 Embedding 是不同阶段。过小片段会丢条件，过大片段影响检索与预算；PDF 表格和扫描件需要另一个范围，不在本轮默认实现。

### M3-D 索引与混合检索

**业务目标**：同租户用户问退货期限时，能检索到正确政策；另一个租户或无内部权限的顾客不能召回禁止片段。

**进入条件**：B/C 可重复运行，Dense、Sparse、Reranker 与资源条件已确认。测试替身用于普通自动化测试，但最终必须使用真实索引与模型验证。

**执行顺序**：

1. 增加 Embedding、Sparse、Rerank 与 Qdrant 适配器，固定 query/document 编码方式、向量维度和配置指纹；Embedding 模型更换需要新 Collection/重建，不直接混写。
2. 为同一 point 建 named dense、sparse vectors；payload 保存 tenant、document、version、chunk、visibility 等最小信息，并建过滤字段索引。
3. Worker 用稳定 point ID 写入，等待写入确认并核对预期 Chunk 完成后才标记 ready 和切换生效版本。
4. 实现 `retrieve(question, identity)`：两路都加后端构造的权限过滤，融合去重，数据库复核，再用真实 Reranker 排序。
5. 增加管理员检索调试入口，返回本租户允许证据的 locator 与各阶段分数，禁止跨用户会话读取，不返回向量、Secret 或全库内容。
6. 用中文同义问法、精确关键词和一个缺失政策问题检查结果；据此设置召回数与门槛。生产召回服务与调试入口复用同一过滤实现。

**预计文件**：`src/aftercare_api/retrieval/{schemas,service,index,embeddings,sparse,rerank,router}.py`、`knowledge/tasks.py`、配置、依赖锁文件、Compose 模型缓存、检索与隔离测试。

**验证与完成条件**：真实 Qdrant 同时存在两种表示，记录两路召回、融合与重排结果；“退货期限”和“收货后多久能退”都找到七天片段。租户 B 的结果和引用不含 A 文档，顾客不返回 staff_only。首次上传流程从 queued 到 ready。

**学习重点与风险**：混合融合不是重排；简单按向量分数排序不能宣称 Reranker 已完成。当前服务器为 `v1.15.4`，官方最新示例可能含更晚功能，实施前验证锁定 SDK 与服务器兼容，不为示例默认升级基础服务。

### M3-E 带引用的知识回答与现有对话集成

**业务目标**：顾客在现有会话里得到有依据的答案，刷新后仍有引用；没有依据时拒答，停止与重新生成仍遵守 M2 契约。

**进入条件**：D 的权限与证据正确；真实生成模型、凭据或本地服务、可用 Tokenizer 和预算已确定。付费调用必须已有明确授权。

**执行顺序**：

1. 建立最小 Generation 适配器：输入问题/预算内证据，输出文本、引用标签与可用 usage；保留明确的 demo/test 模式，不能在真实模式失败时暗中回退为占位成功。
2. 新增引用表和生成快照元数据迁移。把知识证据纳入 `prepare_context` 的最终预算，保存实际发给模型的消息结构与配置版本，区分本地估计和供应商 usage。
3. 冻结属于本次回复的证据，给模型 `[S1]` 等服务端分配标签。文档内容视为数据，不执行其中“忽略规则”等指令；模型输出不得引入未提供来源。
4. 先走“模型生成完整回答 → 校验引用 → 通过现有 SSE 分段发送”的小切片，页面注明当前缓冲行为。最小校验为标签存在、来源在证据集中、主要答案有人工作证；不宣称标签校验等于语义正确证明。
5. 不允许把未经校验内容先发给用户再撤回。真实供应商 Token 流作为后续可批准优化；本阶段缓冲后 SSE 可满足浏览器分段与持久化目标，但首段延迟包含完整模型调用。
6. 证据不足走固定拒答，不调用模型编造；模型/检索不可用给出明确暂时不可用结果。用回答元数据区分 answered/refused/unavailable，unavailable 不伪装为正常知识答案。
7. 接入同步发送、SSE 和重新生成，明确统一知识模式，避免绕过检索走旧同步占位接口。沿用 started/delta/completed/cancelled，不增加矛盾终态；停止时取消本地模型等待/关闭连接，不能保证撤销供应商已经消耗的资源。
8. 重新生成重新检索并绑定新回复的引用。保留旧回复、原上下文与反馈，取消新版本仍保留原当前版本；历史消息无需编造新引用。多轮指代先只用受控历史构造检索问题；“退货要几天 → 运费呢”至少有一个演示验证，不引入完整 Agent 路由。

**预计文件**：`src/aftercare_api/generation/`、`retrieval/service.py`、`conversations/{context,service,models,schemas,router}.py`、迁移、配置、`apps/web/src/conversations.ts`、`HomeView.vue` 与相应测试。

**验证与完成条件**：七天问题回答附真实证据与版本，海外退货费用拒答；真实模型至少一次正常链路通过。新增证据后仍满足输入预算 + 输出预留 ≤ 总预算。引用随回复持久化，停止模型等待/分段发送后状态为取消，重新生成有独立引用且旧反馈不移动。一个供应商不可用测试证明没有占位成功。

**学习重点与风险**：有引用标签不代表内容可靠，仍需逐条对照证据。现有 `cl100k_base` 不自动适配所有供应商；必须使用匹配编码或供应商计数并保留余量。当前默认总预算 4096 可能需要调整，但先削减证据和历史，再决定扩大。

### M3-F 更新删除与知识管理界面

**业务目标**：管理员可以在浏览器管理政策；用户能展开引用，并明确辨别当前、旧版或已删除来源。

**执行顺序**：

1. 新增同文档上传下一版本接口及页面。旧 active 指针保留到新版本完整 ready；界面分别展示生效版和待处理版，不能只用一个“成功”状态覆盖二者。
2. 用七天 → 十五天演示替换；切换后即使旧 points 尚未物理删除，也应被两路过滤和数据库复核排除。异步清理按文档/版本 ID 执行。
3. 删除先写数据库失效，再清理全部版本索引和原文件；记录清理状态，增加最小管理员重试入口。Worker 激活前检查文档未删除，避免恢复已删文档。
4. 增加管理员 `/knowledge` 页面、导航与角色路由提示，包含上传、可见性、状态轮询、版本、错误和删除确认。直接 API 仍执行管理权限。
5. 对话增加文档名/版本/位置引用卡片和受保护的来源展开请求。不要依赖新窗口链接自动携带 Bearer token；用已有认证客户端请求片段，再在页面展示。
6. 来源展开再次检查当前权限：旧版标记“已被替换”，删除来源显示失效提示并禁止从来源接口读原文。已持久化的旧回答可保留历史引用快照，不代表文档仍可检索。
7. 扩展 CORS 的 DELETE 等实际方法，保持允许来源和 Authorization 规则；审计只记录管理动作元数据，不记录上传文件、问题或 Chunk 原文。

**预计文件**：`knowledge/{router,service,tasks}.py`、`retrieval/service.py`、`audit/middleware.py`、`main.py`、`apps/web/src/{knowledge,router,conversations}.ts`、`views/KnowledgeView.vue`、`HomeView.vue`、样式与针对性交互测试。

**验证与完成条件**：正常更新后新问题与重新生成均只引用十五天；删除后新旧版本均不召回，同一旧会话也不会用历史七天/十五天继续回答。顾客直调管理接口为 403。浏览器引用可展开、刷新仍存在，旧版和删除来源标识正确。用一个处理失败样本确认旧 active 保留即可，不扩展完整故障框架。

**学习重点与风险**：逻辑失效保障当前权限，物理清理处理残留数据，是两件不同工作。删除不等于清除既有聊天历史；若未来要求隐私彻底删除，需另行定义消息、快照、备份与保留策略。

### M3-G 全链路验收与交接

**业务目标**：开发者能从空的独立环境复现 M3，并解释每个业务结果由哪些数据与权限决定。

**执行顺序**：

1. 准备两个模拟租户及管理员/客服/顾客；沿用 M2 脚本的测试库限制和交互密码处理原则，新增 M3 专用初始化脚本，不能直接把旧脚本切到长期库。
2. 上传三种格式的合成资料，以及一份 staff_only 内部说明。资料只包含模拟政策，不加入真实客户信息。
3. 建立约 12 个小型问题：明确答案、同义问法、关键词、缺失信息、跨租户、顾客读内部文档、上下文追问、更新后追问、删除后追问、重新生成、来源定位和文档指令诱导。每题记录预期证据/拒答及实际结果。
4. 普通自动化测试使用模型/存储替身；真实 PostgreSQL、Qdrant、MinIO、Worker 与至少一次真实生成另设显式配置的集成演示，不在普通测试里自动下载大模型或产生费用。
5. 独立数据库验证空库升级、M2 带历史数据升级和 M3 迁移回退重升级。确认回退移除 M3 数据与元数据的边界，M2 消息/反馈保持不变；数据库回退不会自动删除外部对象和索引。
6. 浏览器完成管理员上传 → 处理 ready → 顾客问答 → 展开引用 → 刷新 → 停止/重新生成 → 更新 → 删除。记录首段延迟、检索耗时和使用配置作观察值，不设未经测量的 SLA。
7. 更新 STATUS、README、ACCEPTANCE_CASES 和 LEARNING_LOG；必要时补 ARCHITECTURE/DECISIONS，记录真实链路、配置和未完成部分。最终只提交已批准范围；提交、推送、PR 和请求 review 各自单独授权。

**预计文件**：`tests/test_m3_regression.py`、针对性模块测试、合成 fixtures、`scripts/seed_m3_demo.py`、`compose.m3.verify.yaml`、README 与项目文档。

**完成条件**：核心正向演示重复成功，基础租户/角色隔离、无证据拒答和更新删除有验证，M2 既有测试没有回退；没有以模型替身代替真实验收。长期服务与数据未因独立验证被改动。

**学习重点与风险**：自动化测试证明确定性契约，真实模型演示证明当前配置能够跑通，两者不能互相替代。小问题集只证明当前资料和问法效果，不代表通用 RAG 质量或生产容量。

沿用 M2 消息发送、SSE、停止、重新生成和反馈路径，引用作为附加元数据随历史详情/完成事件返回。状态查询不要求新增 WebSocket；短轮询足够。具体响应 Schema 在对应阶段分析并批准后冻结。

| 配置组 | 建议字段 | 确认时间 |
|---|---|---|

## 8 依赖顺序与学习节奏

默认串行：`M3-A → M3-B → M3-C → M3-D → M3-E → M3-F → M3-G`。只读准备资料可以提前做，模型尚未确定时先完成 B/C；不要在另一个窗口同时改变会话、文档或索引契约。

| 阶段 | 建议学习单元 | 阶段结束应看到的结果 |
|---|---|---|
| A | 1 次分析与确认 | 契约和环境选择明确 |
| B | 2 至 3 次开发 | API 上传、存储和任务可查询 |
| C | 2 至 3 次开发 | 三格式产生带定位 Chunk |
| D | 2 至 3 次开发 | 真实混合检索与重排可解释 |
| E | 3 至 4 次开发 | 真实带引用回答、拒答与 M2 兼容 |
| F | 2 至 3 次开发 | 浏览器管理、更新删除、引用展开 |
| G | 1 至 2 次验证 | 独立环境完整复现与交接 |

每次学习单元建议只批准一个可独立验收的小切片。以上是拆分建议，不是工期承诺；模型下载、配置和基础环境问题可能增加时间。B/C/D/E 可进一步拆分，但不能跳过核心验收直接标记阶段完成。

## 11 依据与技术参考

项目依据：[M2 计划](M2.md)、[当前状态](../STATUS.md)、[需求](../REQUIREMENTS.md)、[验收案例](../ACCEPTANCE_CASES.md)、[架构](../ARCHITECTURE.md)、[决策](../DECISIONS.md)、[学习日志](../LEARNING_LOG.md)。代码入口相对仓库根目录为 `apps/api/src/aftercare_api/` 与 `apps/web/src/`。

外部资料于 2026-10-12 查阅，只用于方案依据，具体依赖与模型仍需实施阶段锁定和实测：

- [Qdrant 混合与多阶段查询](https://qdrant.tech/documentation/search/hybrid-queries/)：Dense/Sparse 可通过 Query API 多路召回与融合；这支持沿用一个检索服务的方案。采用现有服务器可用功能，不照搬最新参数。
- [Qdrant FastEmbed 重排](https://qdrant.tech/documentation/fastembed/fastembed-rerankers/)：重排对有限候选重新判断相关性，增加计算成本。候选模型要核验中文表现与用途许可，教程模型不直接作为默认决策。
- [Celery Tasks](https://docs.celeryq.dev/en/stable/userguide/tasks.html)：任务应考虑重复执行；本项目以稳定 Chunk/point ID 和数据库状态提供最小幂等，不承诺崩溃后的自动恢复。
- [pypdf 文本提取](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)：文本提取不等于 OCR，扫描 PDF 需要额外识别能力，因此本轮限定可提取文本的 PDF。
