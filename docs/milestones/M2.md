## 1. 里程碑目标

交付一条可信的基础业务链路：用户能够登录到正确租户，后端能够持续执行身份、角色和租户边界检查；顾客随后能够创建会话、接收流式回复，并在刷新页面后读取历史消息。

M2 不实现知识库检索、真实大模型回答、订单 Tool、工单或部署流水线。M2 的重点是为这些后续能力建立可靠的身份与会话契约。

## 4. M2-A 详细计划

### 业务目标

一个新商家能够创建首个管理员账号，随后登录并通过受保护接口确认自己的用户、租户和角色；账号或成员关系被停用后，之前签发的令牌不能继续访问业务接口。

### 计划范围

- 引入 SQLAlchemy 异步数据访问与 Alembic 迁移。
- 建立最小 `tenants`、`users` 和 `tenant_memberships` 数据模型。
- 在单个事务中完成首个租户与管理员注册，避免半完成数据。
- 使用适合密码存储的算法进行哈希与校验，绝不保存或记录明文密码。
- 签发短期访问令牌，并校验签名、过期时间和必要身份声明。
- 提供注册、登录和读取当前身份的最小 API。
- 在受保护请求中从可信令牌定位身份，并从数据库重新检查用户、租户成员关系及启用状态。
- 为数据库迁移、正常登录、错误密码、重复注册、非法或过期令牌、停用后旧令牌失效等路径添加自动化测试。
- 更新环境变量示例、API 文档和交接文档，但不写入真实密钥。

### 明确非范围

- 前端登录页面和前端令牌管理。
- 刷新令牌、找回密码、邮箱验证、OAuth 或单点登录。
- 邀请更多成员、成员管理界面和完整角色权限矩阵。
- 会话、消息、SSE、RAG、Agent 或 Tool。
- CI、生产部署、提交、推送和创建 PR，除非另行批准。

### 建议接口草案

接口名称与字段需要在 M2-A 只读设计阶段最终确认，当前草案为：

- `POST /api/v1/auth/register-tenant-admin`
- `POST /api/v1/auth/login`
- `GET /api/v1/auth/me`

错误响应应保持统一、避免泄露账号是否存在，并包含可追踪的请求标识。客户端不得通过请求字段自行决定可信租户或角色。

### 验证计划

1. 在空数据库执行 Alembic upgrade，检查表、约束和索引；执行 downgrade 后再 upgrade，证明迁移可重复。
2. 验证注册事务完整性、规范化后的重复账号和重复租户标识冲突。
3. 验证正确密码登录、错误密码拒绝，以及响应与日志不包含密码或完整令牌。
4. 验证缺失、篡改、错误签名和过期令牌均被拒绝。
5. 登录后停用 user 或 membership，确认旧令牌调用 `/me` 被拒绝。
6. 运行后端静态检查和完整测试，再通过 Docker Compose 验证迁移、启动、live、ready 和三个身份接口。
7. 检查最终差异只包含批准范围，不包含 Secret 或无关格式化。

### 主要风险

- 如果只信任令牌里的 `tenant_id` 和角色，停用或角色变化要等令牌过期才生效；因此受保护请求必须重新检查数据库状态。
- 注册同时写入多张表，缺少事务会产生孤立 tenant 或 user。
- SQLite 测试可能掩盖 PostgreSQL 的约束、类型和事务差异；关键迁移与集成行为必须在 PostgreSQL 验证。
- 错误信息、响应时间或日志可能泄露账号存在性和敏感身份数据。
- M2-A 的模型和接口会成为后续会话、RAG 与 Tool 的租户边界，未经测试就继续开发会放大返工。

## 5. 并行工作规则

M2-A 至 M2-C 存在直接契约依赖，默认串行完成。M3 的知识库与 RAG 必须依赖稳定的租户和权限边界，因此不要在另一个窗口同时实现 M3 业务代码。
