## 1. 里程碑目标

交付一条可信的基础业务链路：用户能够登录到正确租户，后端能够持续执行身份、角色和租户边界检查；顾客随后能够创建会话、接收流式回复，并在刷新页面后读取历史消息。

M2 不实现知识库检索、真实大模型回答、订单 Tool、工单或部署流水线。M2 的重点是为这些后续能力建立可靠的身份与会话契约。

### M2-E：上下文预算、摘要与反馈

实现受控消息窗口、Token 预算、长对话摘要和与具体回复版本关联的反馈记录。

完成条件：长对话不会超过配置预算，关键业务事实保留，反馈可追溯。

**实现状态（2026-10-12）**：用户批准先提交 M2-D，再开发 M2-E。已完成正常长对话、预算控制、事实摘录和具体回复反馈；没有引入真实模型或付费调用，没有扩展全面异常测试。新增迁移 `20261012_05`；普通后端 33 个测试、前端 20 个测试、类型检查和镜像构建通过，独立 PostgreSQL 迁移及容器正常演示通过。M2-E 已归入提交 `104c3c0`，实时远程 main 核验相同。以下记录实际交付契约。

1. **当前版本选择**：以用户输入的 `(created_at, id)` 排列轮次，通过 `in_reply_to_message_id` 将每个输入关联到 `role=assistant AND generation_status=completed AND is_current=true` 的唯一回复。历史、生成中、取消回复不作为答案上下文；首个回复取消而没有当前答案时，只保留用户输入及未完成的明确标记。重新生成历史输入时，以该输入为截止点，排除它的所有助手版本及之后轮次，避免让模型看到要替换的答案或未来问题。保存一次上下文快照中的具体消息 ID、摘要 ID 和来源指纹，生成中不会跟随当前标记漂移。
2. **预算**：默认总预算 4096、输出预留/上限 512、摘要上限 1024 Token、最近最多 6 轮，均可配置。满足 `输入计量 + 输出预留 <= 总预算`；输入包括系统说明、摘要、事实、历史轮次、当前输入及实际 JSON 包装。完整提示词使用 `tiktoken 0.14.0` 的 `cl100k_base` 编码计量；快照保存编码、库版本和提示词格式版本。输出按该编码上限截取，原输入仍完整持久化；超过必要事实/当前输入预算返回 `422`。官方编码接口参见 https://github.com/openai/tiktoken。未来接入真实模型时需匹配其实际包装，并区别本地计数与供应商用量；本轮不加入真实模型计费验证。
3. **摘要与事实**：使用确定性事实摘录和剩余空间内的近期用户片段。规则识别订单编号、商品、日期、数量、售后诉求和用户报告状态，每个事实保留来源消息 ID、角色、原文片段；不推断真实业务状态，不从占位助手回声生成新的“已确认事实”。摘要保存覆盖消息 ID（包括当时当前助手版本）、指纹、构造器版本及 Token 数。当前版本变化后，新请求基于新来源构造摘要；原摘要继续服务于旧回复快照追溯。原始消息不删除；任意自然语言事实、通用语义摘要和生产摘要恢复不在本轮保证范围内。
4. **反馈**：已提供 `POST /api/v1/conversations/{conversation_id}/messages/{message_id}/feedback`，提交点赞/点踩、原因枚举和最多 500 字补充。服务端回查租户、会话所有权和消息归属；允许历史已完成版本反馈，拒绝用户消息及未完成版本。`(actor_user_id, message_id)` 唯一约束保护记录，正常重复提交更新原反馈；tenant/user 取认证上下文。已有反馈不会随当前版本移动，也不直接改变摘要或答案。GET 会话返回当前用户的反馈和各回复上下文信息，前端展示并支持刷新恢复。
5. **主要文件**：新增 `conversations/context.py`、`token_budget.py`、`summaries.py`、`feedback.py`、迁移 `20261012_05` 和正常流程测试；调整模型、Schema、服务、路由、配置、依赖锁、镜像与 Compose 配置。前端调整会话类型、页面、样式和反馈测试。旧迁移保持不变，旧回复不伪造上下文快照。
6. **正常流程验证结果**：长对话移出直接窗口后，追问仍从摘要得到订单 42；新上下文只选当前回复，重新生成旧输入不带未来轮次；反馈刷新后仍存在，版本 2 完成后点踩仍属于版本 1。实际提示词重新计量与持久化计数相同，容器演示为 344 输入 + 512 输出预留 <= 4096。PostgreSQL 完成 `05 → 04 → 05`。本轮不重复扩展全部故障演练，AC-020 明确是确定性模拟证据。

**实际限制**：事实摘录仅保证约定格式和关键词，不是通用语义理解；输出可能在 Token 上限截断；大量必须事实超预算会拒绝新增生成。真实供应商计量、生产并发和摘要恢复不在当前学习范围。摘要和提示词包含会话文本，留在受租户/所有权检查保护的数据库中，不写入日志。M2-F 已按用户批准完成最小角色与审计范围，见下节。

## 4. M2-A 详细计划

### 业务目标

一个新商家能够创建首个管理员账号，随后登录并通过受保护接口确认自己的用户、租户和角色；账号或成员关系被停用后，之前签发的令牌不能继续访问业务接口。

### 计划范围

- 引入 SQLAlchemy 异步数据访问与 Alembic 迁移。
- 建立最小 `tenants`、`users` 和 `tenant_memberships` 数据模型。
- 在单个事务中完成首个租户与管理员注册，避免半完成数据。
- 使用适合密码存储的算法进行哈希与校验，绝不保存或记录明文密码。
- 签发短期访问令牌，并校验签名、过期时间和必要身份声明。
- 提供注册、登录和读取当前身份的最小 API。
- 在受保护请求中从可信令牌定位身份，并从数据库重新检查用户、租户成员关系及启用状态。
- 为数据库迁移、正常登录、错误密码、重复注册、非法或过期令牌、停用后旧令牌失效等路径添加自动化测试。
- 更新环境变量示例、API 文档和交接文档，但不写入真实密钥。

### 明确非范围

- 前端登录页面和前端令牌管理。
- 刷新令牌、找回密码、邮箱验证、OAuth 或单点登录。
- 邀请更多成员、成员管理界面和完整角色权限矩阵。
- 会话、消息、SSE、RAG、Agent 或 Tool。
- CI、生产部署、提交、推送和创建 PR，除非另行批准。

### 建议接口草案

接口名称与字段需要在 M2-A 只读设计阶段最终确认，当前草案为：

- `POST /api/v1/auth/register-tenant-admin`
- `POST /api/v1/auth/login`
- `GET /api/v1/auth/me`

错误响应应保持统一、避免泄露账号是否存在，并包含可追踪的请求标识。客户端不得通过请求字段自行决定可信租户或角色。

### 验证计划

1. 在空数据库执行 Alembic upgrade，检查表、约束和索引；执行 downgrade 后再 upgrade，证明迁移可重复。
2. 验证注册事务完整性、规范化后的重复账号和重复租户标识冲突。
3. 验证正确密码登录、错误密码拒绝，以及响应与日志不包含密码或完整令牌。
4. 验证缺失、篡改、错误签名和过期令牌均被拒绝。
5. 登录后停用 user 或 membership，确认旧令牌调用 `/me` 被拒绝。
6. 运行后端静态检查和完整测试，再通过 Docker Compose 验证迁移、启动、live、ready 和三个身份接口。
7. 检查最终差异只包含批准范围，不包含 Secret 或无关格式化。

### 主要风险

- 如果只信任令牌里的 `tenant_id` 和角色，停用或角色变化要等令牌过期才生效；因此受保护请求必须重新检查数据库状态。
- 注册同时写入多张表，缺少事务会产生孤立 tenant 或 user。
- SQLite 测试可能掩盖 PostgreSQL 的约束、类型和事务差异；关键迁移与集成行为必须在 PostgreSQL 验证。
- 错误信息、响应时间或日志可能泄露账号存在性和敏感身份数据。
- M2-A 的模型和接口会成为后续会话、RAG 与 Tool 的租户边界，未经测试就继续开发会放大返工。

## 5. 并行工作规则

M2-A 至 M2-C 存在直接契约依赖，默认串行完成。M3 的知识库与 RAG 必须依赖稳定的租户和权限边界，因此不要在另一个窗口同时实现 M3 业务代码。

可以并行进行的工作仅限真正独立的只读研究、测试数据准备或文档草案。任何并行写代码的任务必须使用独立分支和独立 Git worktree，并先确认修改文件和数据契约不会重叠。
