## 1. 里程碑目标

交付一条可信的基础业务链路：用户能够登录到正确租户，后端能够持续执行身份、角色和租户边界检查；顾客随后能够创建会话、接收流式回复，并在刷新页面后读取历史消息。

M2 不实现知识库检索、真实大模型回答、订单 Tool、工单或部署流水线。M2 的重点是为这些后续能力建立可靠的身份与会话契约。

### M2-E：上下文预算、摘要与反馈

实现受控消息窗口、Token 预算、长对话摘要和与具体回复版本关联的反馈记录。

完成条件：长对话不会超过配置预算，关键业务事实保留，反馈可追溯。

**只读分析（2026-10-12，以下均为待批准方案）**：当前代码没有上下文构造、Token 计量、摘要或反馈模块，也没有模型供应商。按用户最新的学习演示范围，先完成正常长对话、预算控制、事实摘要和反馈追溯，不以穷尽异常处理或并发加固作为完成门槛。M2-E 保持确定性生成器，不调用付费模型；不能把模拟提示词的计量结果宣称为真实供应商账单或真实模型验收。下面的异常与冲突说明是契约边界，默认不开展全面故障演练或恢复机制建设。

1. **当前版本选择**：以用户输入的 `(created_at, id)` 排列轮次，通过 `in_reply_to_message_id` 将每个输入关联到 `role=assistant AND generation_status=completed AND is_current=true` 的唯一回复。历史、生成中、取消回复不作为答案上下文；首个回复取消而没有当前答案时，只保留用户输入及未完成的明确标记。重新生成历史输入时，以该输入为截止点，排除它的所有助手版本及之后轮次，避免让模型看到要替换的答案或未来问题。保存一次上下文快照中的具体消息 ID、摘要 ID 和来源指纹，生成中不会跟随当前标记漂移。
2. **预算**：配置总预算、输出预留、摘要上限和轮次数上限。必须满足 `输入计量 + 输出预留 <= 总预算`；输入包括系统说明、摘要、事实、历史轮次、当前输入及实际提示词包装。优先保留当前输入和必须事实，再从最近的完整轮次向前选取，按原始轮次顺序输出。不得用字符数或英文空格数冒充 Token。建议通过可替换计量接口采用固定编码的 `tiktoken`（官方支持指定编码；参见 https://github.com/openai/tiktoken），保存编码名称、库版本和提示词格式版本，并对最终实际传给确定性生成器的提示词重新计量。以后接入真实模型时必须换成匹配供应商/模型的包装计量器，并分别保存本地预算计数与供应商返回用量。中文、Emoji、长数字、特殊 Token 文本和边界预算都需要测试。
3. **摘要与事实**：首版使用可测试的事实摘录和受控结构，不让占位生成器伪装成通用语义摘要。先约定必须保留的订单标识、商品、时间、数量、用户诉求、已确认操作及未解决问题；每个事实保存来源消息 ID、助手版本 ID（若有）、原文片段和“用户陈述/助手陈述”类型。顾客陈述不升级为已核实的订单状态；后续修正和冲突保留来源，不拼成无出处的事实。摘要记录覆盖轮次、来源版本指纹、构造器版本与 Token 计数；任一覆盖回复的当前版本变化后，旧摘要失效并从原始记录重建。摘要失败、事实本身超预算或当前输入无法容纳时，应明确拒绝本次生成并保持历史，不能丢事实后继续声称成功。摘要不删除原消息，也不反复压缩摘要而遗失来源。任意自然语言事实的自动识别不在这个确定性首版的保证范围内。
4. **反馈**：建议 `POST /conversations/{conversation_id}/messages/{message_id}/feedback`，对具体已完成助手消息提交点赞/点踩、原因枚举和有限长度补充文本。服务端回查租户、会话所有权和消息归属；允许对历史已完成版本反馈，拒绝用户消息及未完成版本。通过 `(actor_user_id, message_id)` 唯一约束实现重复提交更新；字段中的 tenant/user 均取认证上下文。以后当前回复变化，已有反馈仍留在原 message ID，不跟随 `is_current` 移动。反馈不是上下文事实，也不直接改变摘要或答案。
5. **拟修改文件**：新增 `conversations/context.py`、`token_budget.py`、`summaries.py`、`feedback.py` 及相应测试；调整 `models.py`、`schemas.py`、`service.py`、`router.py`、配置、依赖锁和新的 Alembic 迁移；前端调整会话类型、页面和反馈交互测试；更新需求细化、验收、决策和状态文档。不会改写已发布迁移，不接入真实 LLM、RAG、Agent 或真实业务数据。
6. **正常流程验证计划**：用包含订单 42 的长对话演示窗口选择、事实摘录、追问和 Token 预算；重新生成后上下文使用新当前版本；对一个具体回复提交点踩和原因，刷新后仍能读取且版本归属不变。执行新增迁移、相关模块测试、类型检查与一次 Compose 演示即可，不默认扩展全套异常、并发和故障恢复测试。AC-020 首版证据明确标为确定性模拟，实际模型请求预算需在供应商接入后补验。

**待批准范围和风险**：事实摘录的保证必须限定在约定事实类型；未知供应商的真实包装 Token 开销不能预先保证；历史回复版本改变可能让摘要重建增加耗时；超预算拒绝需要明确用户体验；反馈包含用户文本，不应写入日志。实施批准前只保留此设计，不新增 M2-E 表、依赖或接口。

## 4. M2-A 详细计划

### 业务目标

一个新商家能够创建首个管理员账号，随后登录并通过受保护接口确认自己的用户、租户和角色；账号或成员关系被停用后，之前签发的令牌不能继续访问业务接口。

### 计划范围

- 引入 SQLAlchemy 异步数据访问与 Alembic 迁移。
- 建立最小 `tenants`、`users` 和 `tenant_memberships` 数据模型。
- 在单个事务中完成首个租户与管理员注册，避免半完成数据。
- 使用适合密码存储的算法进行哈希与校验，绝不保存或记录明文密码。
- 签发短期访问令牌，并校验签名、过期时间和必要身份声明。
- 提供注册、登录和读取当前身份的最小 API。
- 在受保护请求中从可信令牌定位身份，并从数据库重新检查用户、租户成员关系及启用状态。
- 为数据库迁移、正常登录、错误密码、重复注册、非法或过期令牌、停用后旧令牌失效等路径添加自动化测试。
- 更新环境变量示例、API 文档和交接文档，但不写入真实密钥。

### 明确非范围

- 前端登录页面和前端令牌管理。
- 刷新令牌、找回密码、邮箱验证、OAuth 或单点登录。
- 邀请更多成员、成员管理界面和完整角色权限矩阵。
- 会话、消息、SSE、RAG、Agent 或 Tool。
- CI、生产部署、提交、推送和创建 PR，除非另行批准。

### 建议接口草案

接口名称与字段需要在 M2-A 只读设计阶段最终确认，当前草案为：

- `POST /api/v1/auth/register-tenant-admin`
- `POST /api/v1/auth/login`
- `GET /api/v1/auth/me`

错误响应应保持统一、避免泄露账号是否存在，并包含可追踪的请求标识。客户端不得通过请求字段自行决定可信租户或角色。

### 验证计划

1. 在空数据库执行 Alembic upgrade，检查表、约束和索引；执行 downgrade 后再 upgrade，证明迁移可重复。
2. 验证注册事务完整性、规范化后的重复账号和重复租户标识冲突。
3. 验证正确密码登录、错误密码拒绝，以及响应与日志不包含密码或完整令牌。
4. 验证缺失、篡改、错误签名和过期令牌均被拒绝。
5. 登录后停用 user 或 membership，确认旧令牌调用 `/me` 被拒绝。
6. 运行后端静态检查和完整测试，再通过 Docker Compose 验证迁移、启动、live、ready 和三个身份接口。
7. 检查最终差异只包含批准范围，不包含 Secret 或无关格式化。

### 主要风险

- 如果只信任令牌里的 `tenant_id` 和角色，停用或角色变化要等令牌过期才生效；因此受保护请求必须重新检查数据库状态。
- 注册同时写入多张表，缺少事务会产生孤立 tenant 或 user。
- SQLite 测试可能掩盖 PostgreSQL 的约束、类型和事务差异；关键迁移与集成行为必须在 PostgreSQL 验证。
- 错误信息、响应时间或日志可能泄露账号存在性和敏感身份数据。
- M2-A 的模型和接口会成为后续会话、RAG 与 Tool 的租户边界，未经测试就继续开发会放大返工。

## 5. 并行工作规则
