# 架构决策记录

本文件记录会影响后续实现的重要选择。新的重大选择应追加记录，不通过悄悄改代码改变既有边界。

## ADR-001：采用模块化单体

- **状态**：Accepted
- **背景**：第一版需要同时交付身份、对话、RAG、Tool、工单和部署能力，但只有一个学习者维护。
- **决定**：前端使用一个 Vue 应用；后端使用一个 FastAPI 部署单元，并按业务模块划分内部边界。后台任务使用独立 Worker 进程，但共享后端领域代码和数据库模型。
- **理由**：便于本地启动、事务处理、调试和部署，同时仍能学习清晰边界。
- **代价**：模块不能独立扩缩容；若未来拆分服务，需要重新设计跨模块事务和接口。

## ADR-002：第一版在 Qdrant 中完成混合检索

- **状态**：Accepted
- **背景**：阶段目标要求语义与关键词混合检索。第一版同时维护 Qdrant 和 Elasticsearch 会增加部署、同步和排障成本。
- **决定**：在 Qdrant 中保存 Dense 和 Sparse 表示，通过融合召回后执行 Rerank。PostgreSQL 保存文档生命周期的权威状态。
- **理由**：用一个检索服务完成首版学习目标，减少跨索引一致性问题。
- **代价**：不会在第一版深入学习 Elasticsearch/OpenSearch；如果后续出现复杂全文分析需求，再用评测数据决定是否引入。

## ADR-003：只实现一个受控 Agent

- **状态**：Accepted
- **背景**：核心流程需要在知识检索、业务 Tool 和人工服务之间路由，但不需要多个自治 Agent 协商。
- **决定**：使用 LangGraph 实现一个节点明确、步骤有上限、状态可持久化的工作流。
- **理由**：可以学习状态、Checkpoint、Tool 和恢复，同时保持行为可测试。
- **代价**：复杂流程需要显式增加节点，不能依靠多个 Agent 自由协作解决。

## ADR-004：业务系统使用模拟数据

- **状态**：Accepted
- **背景**：学习项目不应操作真实订单、支付、退款或客户隐私数据。
- **决定**：在 PostgreSQL 中构造模拟订单、物流、退款和工单；Tool 接口按未来外部集成边界设计。
- **理由**：保留真实的权限、事务、幂等和失败语义，同时避免外部账号、合规和资金风险。
- **代价**：项目不能证明某一真实电商平台的集成细节，需要在未来集成时补充适配层和契约测试。

## ADR-005：受控 Beta 使用单机 Docker Compose

- **状态**：Accepted
- **背景**：第一版的重点是完整上线链路，而不是 Kubernetes 运维。
- **决定**：使用一台 Linux 服务器和 Docker Compose 部署，配合 HTTPS、健康检查、持久化卷、备份和回滚步骤。
- **理由**：在较低基础设施复杂度下学习镜像、迁移、部署和恢复。
- **代价**：单机存在可用性上限，不适合作为大规模或严格高可用方案。

## ADR-006：Compose API 启动前执行 Alembic 升级

- **状态**：Accepted
- **背景**：M2-A 引入持久化身份数据后，API 若在空数据库或旧结构上启动，会在首个认证请求时失败。
- **候选方案**：由开发者手动执行迁移；在 Compose 中增加独立迁移服务；由单机 Compose 的 API 启动命令执行迁移。
- **决定**：当前受控 Beta 的单机 Compose 环境中，API 容器先执行 `alembic upgrade head`，成功后才启动 Uvicorn。生产部署前仍需将迁移作为独立、可观测的部署步骤重新评估。
- **理由**：本地环境可以从空数据库重复启动，且迁移失败会阻止新 API 进程变为健康状态。
- **代价**：未来多副本部署不能沿用此做法，否则并发启动可能竞争迁移锁；必须改为单独的迁移步骤或 Job。
- **验证方式**：在 Docker Compose PostgreSQL 上演练 `upgrade → downgrade → upgrade`，再验证 API 健康检查和认证接口。

## ADR-007：将回复版本与生成生命周期持久化

- **状态**：Accepted
- **背景**：SSE 连接会中断，用户也可以主动停止或重新生成回复。仅在内存中保存流状态会导致刷新后无法辨别未完成回复，也无法保留历史答案。
- **决定**：每条助手回复关联其用户输入，并持久化版本号、生成状态和当前版本标记。新版本只有完成后才取代当前版本；取消版本保留已生成内容，但不会成为当前版本。
- **理由**：停止、断连、刷新和重新生成都能由数据库中的可验证状态恢复，不依赖客户端内存。
- **代价**：消息读取会返回多个历史版本；后续界面需要提供更清晰的版本选择体验。
- **验证方式**：自动化测试验证流式完成、停止持久化、版本递增、旧版本保留和当前版本切换。

## ADR-008：回复终态由数据库条件更新决定

- **状态**：Accepted（2026-10-12，用户批准 M2-D 加固范围）
- **背景**：先读取 ORM 状态再提交会让停止和完成互相覆盖；最大版本号加一无法独立保证并发唯一性；ASGI 取消还可能打断同一请求会话的清理。
- **决定**：分段、停止、完成均带 `generating` 条件；终态不可转换。同一输入的重新生成通过来源行锁串行分配，已有生成返回 `409`，并以唯一版本、唯一运行任务及唯一当前版本约束兜底。仅已完成回复可以成为当前，新版本完成和旧当前标记撤销在一个事务中执行。
- **清理边界**：首帧和响应发送失败都纳入收尾；回滚请求事务后以独立、取消保护的事务执行幂等取消，最长等待 3 秒。进程强制退出或数据库不可用时无法保证在线收尾，必须停止所有生成进程后执行 README 的离线恢复，不能在其他进程仍工作时批量取消。
- **历史迁移**：保留旧迁移，新迁移从完整占位文本与严格先前的用户输入中修复可确定来源；修复重复历史版本 1，保留有效版本号和原文。歧义、孤立、冲突版本及损坏来源阻止升级，并由事务回滚保护原数据。回退结构不会重新引入已经修正的错误来源。
- **代价**：同一输入无法同时跑多个候选生成；部分旧数据需要人工确认后才能升级；离线恢复属于单机运维流程，尚不是自动任务恢复。
- **验证方式**：SQLite 生命周期测试、PostgreSQL 独立连接和约束测试、带历史数据的升级/回退/失败回滚、真实 HTTP 断连、浏览器停止与整套 Compose 重启持久化。

## ADR-009：学习演示使用明确 Token 编码、事实摘录和版本反馈

- **状态**：Accepted（2026-10-12，用户批准 M2-E 正常流程开发）
- **背景**：M2 没有模型供应商，但需要学习上下文预算、长对话信息保留和反馈追溯。不能用字符数代替 Token，也不应引入通用语义摘要或生产恢复系统扩大当前范围。
- **决定**：以紧凑 JSON 渲染系统说明、来源摘要、当前回复窗口和本次输入；使用锁定版本的 `tiktoken / cl100k_base` 计量，预留并限制输出。每条新回复保存实际提示词及消息/摘要来源快照。窗口按用户轮次选择唯一已完成当前回复，重新生成历史输入排除未来轮次。
- **摘要边界**：使用订单、商品、日期、数量、售后诉求和用户报告状态的显式规则及原文摘录。事实有消息来源，不升级为已核实业务事实；覆盖的助手版本变化后构造新来源指纹。保留原消息及旧快照，不使用真实模型生成摘要。
- **反馈**：一名用户对一条具体已完成助手消息保存一条可更新的点赞/点踩及原因；历史版本反馈不跟随新当前版本移动。所有读写由后端认证上下文和会话所有权保护。
- **代价**：仅能演示约定格式的事实召回；本地提示词 Token 与真实供应商用量不同；没有生产级摘要恢复或反馈并发重试。旧回复没有追补的生成快照。
- **验证方式**：三个后端正常流程测试、前端反馈和预算展示测试、独立 PostgreSQL 新迁移升级/回退/重升级，以及包含订单 42、344 输入 Token 和版本反馈的 Compose/浏览器演示。

## 新 ADR 模板

```markdown
## ADR-NNN：标题

- **状态**：Proposed / Accepted / Superseded
- **背景**：为什么需要做决定？
- **候选方案**：考虑过哪些选择？
- **决定**：最终选择什么？
- **理由**：为什么？
- **代价**：失去了什么，新增了哪些风险？
- **验证方式**：用什么数据或测试判断决定是否正确？
```
